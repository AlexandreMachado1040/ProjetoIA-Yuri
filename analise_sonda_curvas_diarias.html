Análise — sonda_curvas_diarias.html

Data: 11/06/2026 Arquivo: 51,5 kB · 1.429 linhas · página única Objetivo: decidir se/como integrar ao Aurova Motor
Veredito

O HTML é um excelente protótipo de UX com um motor de dados descartável: as curvas são 100% sintéticas, geradas no navegador. A recomendação é portar a experiência (explorador de dia a dia, calendário, KPIs, HSP), não o código — reconstruindo a tela em React/Recharts alimentada pelos dados reais do nosso Worker. Adendo (seção 5): verificado o repositório do SONDA/INPE, a integração de dados medidos sobe para "viável como fase 2" via pré-processamento offline — sem alterar a recomendação principal.

1 Stack e construção

Página única autocontida, sem framework e sem etapa de build:

CamadaTecnologiaObservação
UI HTML + CSS puro Variáveis CSS, flexbox/grid, tema escuro; visual de aplicativo desktop (menubar, toolbar, sidebar, statusbar)
Gráfico Chart.js 4.4.1 via CDN Única dependência externa; linha com 2 eixos Y, área, tracejado, tooltip customizado
Lógica JavaScript vanilla Funções globais e onclick inline; estado em variáveis soltas
Dados Sintéticos, gerados no navegador PRNG (LCG + Box-Muller) com semente fixa por dia + climatologia mensal de Brasília embutida

Funcionalidades implementadas: navegação por dia/mês (botões, seletores, minicalendário clicável e setas do teclado), toggles de curvas (GHI / DNI / DHI / Temperatura / Céu limpo), KPIs do dia (totais, HSP, temperatura e vento médios, pico e hora do pico), estatísticas do mês, tabela horária e exportação CSV.

2 Ponto crítico: os dados são falsos

Apesar do título "SONDA/INPE — Estação BRB", a página não carrega nenhum dado real do SONDA. Tudo vem de um gerador pseudoaleatório sobre um modelo físico simplificado:

ComponenteO que fazAvaliação
Geometria solar Declinação, ângulo horário, cosseno do zênite Correta, mas básica
Irradiância Beer-Lambert genérico com fator arbitrário kt × 1,3 e tetos fixos (GHI ≤ 1200, DNI ≤ 1000 W/m²) Menos rigorosa que o nosso motor (Spencer + Collares-Pereira + Erbs + Hay & Davies)
Nuvens / chuva Sorteio: 25% de chance de "chuva" na estação chuvosa, autocorrelação horária 0,8 Plausível visualmente, sem base em medição
Climatologia Constantes mensais de kt, temperatura e vento de Brasília fixas no código Só vale para BRB; não acompanha a localização do usuário
⚠ O próprio CSV exportado admite a origem sintética
# Modelo físico: dados sintéticos baseados em climatologia BRB 2018

Manter o selo "SONDA/INPE" sem usar dados do SONDA seria enganoso num produto que se propõe profissional.

3 O que aproveitar e o que descartar

Vale a pena portar
  • Conceito de "explorador de dia a dia" com minicalendário
  • KPI de HSP (hoje não mostramos no dashboard)
  • Toggles de curva GHI / DNI / DHI / Temperatura
  • Curva de céu limpo como referência visual
  • Tabela horária + estatísticas do mês
  • Navegação por teclado (setas)
  • Paleta escura compatível com o nosso tema
Não importar
  • Gerador sintético — temos dados reais (NASA POWER) e decomposição horária real no Worker
  • Chart.js — somos React + Recharts; 2ª lib de gráfico custa ~200 kB e duplica padrões
  • Página estática separada — viraria uma ilha desconectada da simulação do usuário
  • Marca "SONDA/INPE" sem dados do SONDA
  • Climatologia fixa de Brasília

4 Recomendação de implementação

Criar um componente React "Explorador Diário" no dashboard do Aurova, alimentado pelo Worker com dados reais — as curvas refletirão a localização e a configuração reais do usuário, coisa que o HTML nunca faria.

Expor as séries horárias que o motor já calcula Backend · ~1 h

Estender o endpoint /daily (ou criar /dia) para devolver, para uma data escolhida: GHI, DNI, DHI, GHI de céu limpo e G no plano, hora a hora. Hoje essas séries existem internamente (Erbs / Collares-Pereira) mas só saem agregadas.

Componente React com Recharts Frontend · ~3-4 h

Minicalendário + navegação de dia/mês, gráfico com toggles de curvas (2 eixos Y para temperatura), KPIs do dia (GHI total, HSP, pico e hora do pico) e tabela horária — no tema escuro atual.

Integração no dashboard Frontend

Posicionar junto ao DailyEgridChart existente, reaproveitando o inputPayload da simulação corrente (lat/lon, inclinação, azimute).

Risco: baixo — nenhuma dependência nova. Esforço total estimado: 4 a 5 horas.

5 Adendo: coleta de dados reais do SONDA — a avaliação muda?

Verificação feita em 11/06/2026 diretamente nas fontes: sonda.ccst.inpe.br/acesso_dados.html (catálogo de estações e licença) e sonda.ccst.inpe.br/est_brasilia.html (página da estação Brasília — BRB, com os links de download). O acesso é mais simples do que o assumido na primeira avaliação:

AspectoO que foi verificado
Cadastro / login Não exigido — download direto por link
Formato Arquivos ZIP por estação e mês ou ano (ex.: BRB_2018_SD.zip, BRB_2018_01_SD.zip), com tabelas ASCII dentro
Resolução Médias minuto a minuto (≈ 43 mil linhas/mês por estação)
Variáveis (BRB) GHI, DNI, difusa, onda longa, PAR, iluminância. Temperatura e vento NÃO disponíveis em BRB — mais uma prova de que o HTML analisado inventou essas curvas
Cobertura 21 estações no Brasil; BRB tem 2004-2005 e 2010-2018, com lacunas (cobertura não uniforme)
Licença CC BY 4.0 — uso livre com atribuição, inclusive comercial
API Inexistente — apenas download manual de arquivos

O que muda na avaliação

A integração SONDA sobe de "projeto à parte, não recomendado" para "viável como fase 2" — o acesso livre, sem cadastro e com licença CC BY 4.0 elimina as barreiras de obtenção. Mas a forma de integrar é decisiva:

Caminho viável — pré-processamento offline
  • Baixar os ZIPs uma única vez (script local, fora do Worker)
  • Agregar 1 minuto → horário e aplicar os flags de qualidade
  • Publicar JSON compacto por estação/ano como ativo estático (Pages ou R2)
  • No Explorador Diário: toggle "Modelo (NASA POWER)" × "Medido (SONDA)" quando a localização estiver perto de uma estação
  • Validação do motor contra medições de solo vira subproduto natural
Caminho inviável — coleta em tempo de execução
  • Worker baixando/descompactando ZIPs de vários MB a cada requisição
  • Parsing de ~43 mil linhas/mês dentro do limite de CPU do Worker
  • Sem API: nenhuma consulta pontual por data — só o arquivo inteiro
  • Cobertura limitada a 21 pontos não substitui o NASA POWER (global)
  • Lacunas e meses ausentes exigiriam fallback complexo em produção

Conclusão revisada

A recomendação principal continua a mesma: portar a UX com dados reais do nosso motor (NASA POWER) — o SONDA não a substitui, pois cobre apenas 21 pontos e tem lacunas históricas. O que muda é o destino do SONDA: deixa de ser descartado e entra como fase 2 planejável (pipeline offline + ativos estáticos + toggle "medido × modelado" no Explorador Diário), com esforço estimado de 1 a 2 dias e o bônus de validar o motor contra medições de solo. Com dados reais do SONDA no ar, inclusive o selo "SONDA/INPE · CC BY 4.0" passaria a ser legítimo — bastando a atribuição exigida pela licença.

6 Referência: como o PVSyst consome o mesmo tipo de dado (TMY)

Avaliação da ferramenta de geração de TMY do PVSyst 7 (help-pvsyst7/meteo_tmy_data_generation.htm), que faz exatamente o consumo em questão: transformar anos de medições horárias de solo (como as do SONDA) em uma série única utilizável na simulação.

O que o PVSyst faz

AspectoAbordagem do PVSyst
Entrada Mínimo de 10 anos consecutivos de arquivos horários .MET — mesma origem e local, anos completos (janeiro a dezembro), sem duplicatas
Saída Um TMY (Typical Meteorological Year): ano de 8.760 horas montado escolhendo, para cada mês do calendário, o mês real mais representativo do histórico — preserva a variabilidade real (nuvens, sequências de dias ruins), que a síntese a partir de médias não tem
Métodos ISO 15927-4:2005 (norma europeia), Sandia (TMY2/NREL), NREL NSRDB atualizado (TMY3+), e pesos personalizados
Variantes TGY (peso na irradiância global — o caso fotovoltaico) e TDY (peso na direta normal — concentração/CSP)

O que isso significa para o Aurova

O PVSyst confirma que existem dois caminhos legítimos para alimentar um motor de simulação — e nós já temos um deles:

CaminhoPVSystAurova hoje
Síntese a partir de médias Geração sintética horária a partir de médias mensais (Aguiar & Collares-Pereira) ✅ Equivalente: NASA POWER mensal → horário via Collares-Pereira + Erbs
TMY de medições reais Ferramenta TMY sobre ≥10 anos de dados horários medidos ❌ Não temos — é exatamente o que o SONDA viabilizaria

E o SONDA/BRB encaixa quase perfeitamente no requisito de entrada: 2004-2005 + 2010-2018 somam ≈ 10-11 anos de medições minuto a minuto — no limiar do mínimo exigido pelo PVSyst (a ressalva são as lacunas, que a norma ISO 15927-4 tolera até certo ponto ao selecionar meses representativos).

Conclusão do adendo

A referência do PVSyst reforça e dá metodologia profissional à fase 2: em vez de consumir o SONDA de forma improvisada (só exibir dias medidos), o caminho correto é o mesmo do PVSyst — pipeline offline que agrega 1 min → horário, aplica controle de qualidade e monta um TGY por estação (estatística de Finkelstein-Schafer, ~200 linhas de código). O TGY de 8.760 horas entra então no motor como fonte meteorológica alternativa de nível PVSyst, selecionável quando o projeto estiver perto de uma das 21 estações. A recomendação principal não muda: NASA POWER segue como padrão global; o TGY/SONDA vira o diferencial de precisão onde houver estação.
